# 成熟度、证据与风险判断

适用性、执行状态、成熟度和证据可信度分别记录，不压成一个总分。任何等级只适用于声明的项目/变更、风险和验证范围。

## 1. 适用性

- **适用**：当前语言、架构或用户承诺需要该类证据，说明对应风险。
- **条件适用**：取决于尚待确认的原生组件、数据、部署、外部依赖或使用方式；列出条件和调查入口。
- **不适用（NA）**：有技术或业务依据，并说明排除范围；不能因工具未安装、实现成本高或证据找不到而标 NA。
- **待确认**：尚不能判断。先调查，不把未知当作零分或已经缺失。

## 2. 执行状态

| 状态 | 所需证据与含义 |
| --- | --- |
| 已执行通过 | 有对应范围的真实执行结果、完成状态及可定位原始证据；注明版本与环境。 |
| 已执行失败 | 有具体失败、反例或未满足要求；区分产品缺陷、验证器缺陷、夹具错误和环境失败。 |
| 阻塞/未完成 | 缺依赖、超时、权限不足或只有部分输出，不能称通过；记录已完成和未完成范围。 |
| 已配置未证实执行 | 找到脚本/测试/CI 配置，但没有匹配目标的执行记录；不能仅凭命令存在提升为通过。 |
| 仅历史证据 | 结果绑定旧版本/旧环境，尚未证实适用于当前目标；保留原身份和可复用依据。 |
| 未知/未找到证据 | 在说明的仓库、CI、报告等范围内暂未找到；不直接断言作者从未测试。 |
| 确认未建立 | 有明确声明或充分范围内的核查，确认尚无适用检查；注明确认依据及范围。 |
| 明确延期 | 保留原始要求、编号、原因及当前未满足结果；延期不等于完成或不适用。 |
| 不适用 | 必须给出本节第1项的适用性理由。 |

“部分”用于描述上述状态的不同子范围，例如本地通过而生产环境未知；必须展开边界，不能用“部分覆盖”隐藏具体缺口。CI 排队、运行中、取消或部分 job 通过，不构成整个工作流通过。

## 3. 成熟度画像

等级表示验证机制的能力，不表示当前候选的合格结论。能稳定检出真实缺陷的检查即使当前失败，也可具有较高成熟度；同时应清楚报告发布风险。

| 等级 | 判定门槛 |
| --- | --- |
| U | 尚无足够证据判断，或只能看到不可核实的宣称；不折算为 M0。 |
| M0 未建立 | 在明确范围内确认缺少适用的验证机制，或只有没有实际验证内容的占位入口。 |
| M1 已定义 | 有可定位的验证代码/规则、检查目标、命令及明确范围；执行与有效性证据仍有限。 |
| M2 可复验 | 有绑定目标版本与环境的原始执行结果、具体断言/判据及复现方式，能区分通过、失败与未完成。 |
| M3 有检出证据 | 在 M2 基础上，相关故障被真实检查检出，或有适合该风险的独立校验/反例与恢复对照；证明检查能发现其声称防护的问题。 |
| M4 持续治理 | 在相应风险范围内满足 M3，并有持续执行/CI 门禁、版本与漂移约束、证据留档、缺口/例外及责任维护机制。不能只凭 CI 配置存在认定。 |
| NA | 已说明不适用范围，不参与等级比较。 |

不得为所有方法强加同一种负对照。静态规则可用已知违规样例校验；模型检查需要对应真实实现和完整探索证据；代码审查可用独立复核和缺陷闭环；AI 质量评估需要可靠判据与真实任务结果。独立性要说明检查路径、判据来源和模拟边界，不能仅以“另一个代理看过”替代专业检出证据。

不按测试数量、工具数量、文档长度或图谱覆盖比例打分，不对21项求平均。一个范围很窄的 M4 检查不能为未覆盖的关键业务能力背书。报告每层的等级、可信度和阻断因素；同层差异较大时拆分子范围。

## 4. 证据可信度

- **低**：仅摘要、口头宣称、未执行配置、身份不明/缺原始日志，或目标版本无法对应。
- **中**：有可读原始结果和大部分身份信息，但缺关键环境、完整性、判据或独立核对；指出具体不足。
- **高（限声明范围）**：版本/命令/工具/环境可追溯，结果完整，原始日志与断言相符，并有独立读回或适合风险的交叉核对。

可信度判断的是证据对当前声明的支持程度。哈希证明文件身份/完整性，不单独证明性质；日志完整不意味着测试充分；生产器生成并自检的摘要不自动成为独立验证。保留版本差异、模拟边界、排除项与反例，必要时下调结论范围而非编造确定性。

## 5. 八个风险层

| 风险层 | 审计问题 |
| --- | --- |
| 需求与验收 | 关键用户承诺、禁令、失败条件是否清晰可观察，场景是否真正执行，延期是否保留？ |
| 静态质量 | 语言/类型、规则、安全静态检查对当前代码和构建入口覆盖到哪里？ |
| 行为与接口 | 纯行为、真实接线、接口契约和端到端结果是否形成有效且不重复的保护？ |
| 状态与恢复 | 停止、并发、重试、权限/版本变化、崩溃及未知效果是否有模型、事件顺序和真实恢复证据？ |
| 安全与供应链 | 输入/授权/隔离、密钥、依赖漏洞与许可证风险有哪些证据，哪些仍未知？ |
| 运行质量 | 真实环境、规模、性能、资源、长稳、平台和故障预算是否符合使用场景？ |
| AI 实际效果 | 若适用，真实模型/数据能否达成目标；质量、鲁棒性、权限遵守、成本与时延如何？ |
| 证据与持续治理 | 结果是否匹配当前版本，CI 是否真实执行，判据有无检出力，历史/延期/例外是否可追溯？ |

方法是证据来源，风险层是决策视角。先列关键风险及其证据链，再给成熟度画像。无需 AI 的项目将 AI 层标 NA；没有状态生命周期的简单组件不必强造状态机或形式化模型。

## 6. 缺口与建议优先级

- **P0 立即处理**：已证实关键承诺被破坏，或有可定位的高影响安全/数据/权限/恢复缺陷；给出复现和影响，不仅给工具名称。
- **P1 优先补强**：关键路径缺少必要验证或证据失效，现有结果无法支持当前使用/发布承诺；说明最小补证据方式和风险假设。
- **P2 计划改进**：非关键范围或效率、可维护性、持续治理存在缺口；建议与成本、收益及现有保护相称。
- **调查项**：尚不清楚证据是否存在或方法是否适用。说明要定位的资料/实验和潜在影响；不能把未知直接升格为已确认的高危缺陷。关键风险的不确定性可使调查优先，但仍须标注未确认。

每条建议包含：对应承诺/风险、实际证据、尚未支持的结论、最小改进、优先级理由和可观察完成条件。命令从真实项目中提取；尚无入口则写明待建立，不编造已可执行脚本。工作量估计注明假设，不虚构负责人、期限或用户批准。

复用现有场景、模型、夹具或 CI 能解决的问题优先复用；不为凑齐层次重复写单测，也不为小改动默认启动所有昂贵验证。没有采用某个品牌工具、定理证明、原生消毒器或行业标准，不独立构成缺陷。

风险接受是用户/项目责任方的决定。报告已批准例外的来源、范围、理由及有效条件；审计者不能自行将缺口改成接受，也不能删掉原要求制造通过。审计请求本身不授权自动修复、付费调用、破坏性实验或外部发布；继续遵循会话已有授权，不另设一律确认的门槛。
