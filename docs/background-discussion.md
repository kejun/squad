# 工作期间的后台讨论：评估与设计

## 问题与证据

用户在方案师请求执行期间说“所有人都参与讨论一下”，期望协调员组织空闲成员、整理结果，再交由原方案师继续完善方案。基线 6402ddf 的真实 TeamEngine 提交、领取接口可稳定复现：该措辞未建立评审；改成“大家都提提意见”虽建立 review 队列，但 pending 仍为空。任务领取禁止第二个在途请求，WebService 又按整个群串行等待 runOne，故只修改关键词或提示词无法兑现需求。

## 合理性与替代方案

需求合理：成员提供角色视角，协调员负责组织和信息压缩，原负责人保留最终判断与交付责任。只在用户直接邀请时启动，避免默认每个问题都扩大为昂贵讨论。参照 [OpenAI manager 模式](https://openai.github.io/openai-agents-js/guides/multi-agent/)及 [LangChain 子代理同步与异步模式](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)：集中保留最终答复责任、隔离咨询上下文是成熟做法；后台执行的响应性收益伴随并发、恢复和上下文交接成本。本设计借鉴模式，不引入上述 SDK。

| 方案 | 用户价值 | 代价与结论 |
| --- | --- | --- |
| 扩充关键词后沿用串行评审 | 能识别原话 | 仍等待方案师，不能满足工作期间响应 |
| 取消方案师，再开始评审 | 调度简单 | 浪费已付费工作，可能丢失当前产出 |
| 让成员直接修改主方案 | 表面上快 | 多个写入者、最终责任和交付冲突 |
| 独立后台讨论，边界汇入 | 利用空闲成员，保留已有成果与负责人 | 需要显式轮次、互斥、预算和恢复；采用此方案 |

## 范围与约束

直接用户集体邀请在成员工作执行期间创建讨论轮次；已有非并行评审继续沿用原机制。初始目标只来自可信入口解析，模型不能扩大成员范围。排除负责人和已有 pending/inflight/uncertain 工作的成员；本轮跳过的成员及原因立即可见，不在其空闲后偷偷补派。没有空闲成员或预算不足时直接回应，不启动空转模型请求。同群最多一轮未交接的后台讨论；重复邀请记录并说明复用当前轮次。

协调员安排一次，成员每人提供一次独立意见，协调员汇总一次。成员收到当前目标、已有资料、草稿、请求原文和明确问题；不假装可读取方案师尚未返回的隐藏推理。结果保留成员身份、完整文本、报告与失败原因；汇总区分共识、分歧、依据、风险、建议和缺口，不能以多数意见冒充事实或把摘要替代原始证据。

主工作与讨论不互相取消。一个成员同时最多一份工作，协调员的安排、汇总与原监督请求也互斥。并行只发生在不同成员的已持久化且通过领取校验的只读咨询中。主流程仍保持原有顺序约束，不增加任意并发调度入口。

在途模型请求无法可靠注入新上下文，因此讨论先完成时只保存交接材料，等待原请求结算；方案师先返回时保存草稿，等待讨论。两者均完成后才安排原方案师续办一次，再走原完成检查。普通补充仍经原输入解析和安全边界；目标版本或人类决定改变时取消旧讨论，旧结果不进入新版任务。

## 费用与失败

有 N 位成员实际参与时，讨论通常增加 N+2 次普通请求（安排和汇总各一次），随后还需一次负责人续办。沿用普通与协助额度，安排前以及每次请求前为协调员汇总、负责人续办保留容量；格式修正和工具请求也受同一预留限制。额度不能容纳全部成员时减少参与人数并列明缺口，不宣称全员完成。

成员失败或超时结算为缺口，其余成员继续；安排失败结束本轮收集，汇总失败使用带身份与故障说明的确定性原始结果清单交接，不伪造协调员模型成功。存在缺口时最终按部分完成交付。停止同时取消主请求与讨论；取消前保存的结果保留，停止后的结果不得触发派发。重启仅重放安全未完成操作，结果与队列推进在一次事务中保存，重复恢复不能重复发言。配置、成员权限及模型绑定改变沿用恢复暂停规则。

## 验收

features/23_background_discussion.feature 定义 BT_T01–BT_T17。自动化以可控模型和 SQLite 验证实际领取、并发执行、两种结果到达顺序、阻塞后接续、故障与预算、去重、停止、版本隔离、恢复、不同群隔离、领取拒绝后让出执行，以及网页宿主在主请求未返回时实际调用其他角色。受控传输验证协议和执行顺序，不声称验证了真实供应商的回答质量或外部费用。
