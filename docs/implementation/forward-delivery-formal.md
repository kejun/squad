# 单向交付的形式化维护

用户要求：按新流程核对并更新形式化验证。前序业务约束为下游直接补救、采用最新结论、缺口在内容声明后正常交付、交接不回到上游。

## EARS 与核查

- FFM-01：当当前检查返回有效的通过、失败或未核实结论时，系统应直接交付结果；失败或未核实项应在正文声明，保留原判断状态。
- FFM-02：当下游直接修正当前文件时，系统应保留旧稿，在同一文档链创建下一修订并原子发布；不得派回作者或重跑已结算子任务。
- FFM-03：如果检查协议反复无效，则系统应在一次协议补试后明确结束；网络补试与检查请求应按现有配置计费，不重新引入修订许可。
- FFM-04：当旧目标、旧候选、旧尝试或停止后的结果返回时，系统应保留原身份与停止边界；实际未决效果不得因内容交付而丢失。
- FFM-05：当被覆盖实现发生变化时，验证应先记录原样结果，逐项审查代码到模型对应，再更新模型、回放和真实源码负对照；完整运行与独立证据读回通过后才推进同步提交。
- FFM-06：如果形式化回放发现真实实现违反现有业务承诺，则应保留反例，按前序已授权的流程修复范围单独提交产品修复，不放宽性质或混入验证提交。

核查：FFM-01–04 重述已接受的新流程，FFM-05 对应本次维护请求；FFM-06 不增加业务行为，保留既有文件版本与防数据丢失要求。有限模型与实现对应检查分别报告，不声称 TypeScript 全历史等价。

## 性质处置

| 原性质或假设 | 当前性质与承接 |
| --- | --- |
| ModelNeedsValidation：验证成功后才可请求检查 | 允许下游提前检查和补救；HonestVerification 要求缺失/失败/版本不同的验证进入正文，且文件不能冒充已验证 |
| Cycles 检查失败返回 owner | 同一 CHECK_RESULT 直接修正并发布，三次明确用户周期和四个文档修订边界保留 |
| CheckBudget 自动修订计数及免费检查许可 | 单检查工作、五次已配置请求、最多两次恢复；实际 MAX 网络重试配置下逐次收费，反复协议错误明确退出 |
| MapRecovery 逐片申报/验收/引用复审 | ForwardDelivery 的 NoReviewBackflow、DeclaredGaps、CurrentVerdict、HistoryImmutable 及独立 Progress |
| 旧自动修订验证额度预留 | 原前提已经删除，退休该切片；保留成员评审、协助重试与宿主续办的共享额度保护 |
| 授权、停止、来源冻结、未知效果、原子交接 | 保留原性质与有限域，审查新交付写入口及依赖后复验 |

ForwardDelivery 从两个已结算分片（成功、失败）、一次归并和已领取负责人开始，覆盖单次提交、检查领取/消费、三种有效结论、一次直接修正、旧候选、停止、换目标、一次存储重开与一次提交失败。Progress 依赖重开与可执行推进的弱公平，不保证供应商返回。最新结论的历史快照输入独立核对，不能算成 TLC 可达业务历史。

故障对照补强：耗尽 checks 后不能预留无资金的补试，用 BoundedChecks 直接报告行为。失败子结果同时核对公开 Store 原始快照与最终投影；实际规范化在事务提交前执行，单独删除前置置空分支不会破坏承诺，因此故障对照改坏规范化的最后写入点，验证真实错误载荷被检出。此处是夹具与性质增强，没有新的产品缺陷；其余七入口的已完成证明不重复运行。
