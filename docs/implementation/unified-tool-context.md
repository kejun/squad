# 统一工具上下文与执行前授权

## 原始要求与范围

用户要求把沙盒与宿主工具的元信息全量合并为模型上下文，由模型直接选择工具和执行环境；宿主执行的授权在选定具体调用后提出，不以沙盒失败为前置条件。用户同时要求考虑工具信息变化及实时获取的性能成本，目标是工具选择快且准确，并明确同意“全量精简元信息、后台共享快照、选中工具执行前核验”的方案。

本次的“全量”指服务确实接入、已注册且当前角色获准使用的工具能力索引，包括内置网页工具、CLI 的沙盒和宿主环境变体，以及本地技能元信息。帮助全文、技能正文和密钥不进入该索引。系统不会把未接入的 MCP、未知登录态或未扫描的技能源虚构为已知能力。

直接选择宿主不要求预先制造沙盒失败。若已经实际执行的沙盒命令出现明确权限或网络边界签名，且任务需要宿主能力，仍保留 BT_L31 的既有恢复要求：在宣告无法完成或要求用户粘贴内容前，先提供该具体宿主调用的授权路径。提出授权请求不等于执行或获准，普通业务错误、效果不明及原有执行守卫继续按既有规则处理。

## 模型与实现顺序

验收定义为 `features/65_unified_tool_context.feature` 的 BT_Y121–BT_Y130，并修订 BT_L117、BT_L118、BT_L124 对工具展示的要求。状态图见 `docs/state-diagrams.md` 的“统一工具上下文与目录快照”。

目录发布属于宿主内存快照生命周期，模型上下文属于只读投影；二者不新增任务业务阶段，也不从网页或适配器生成命令执行。真实任务 XState 继续拥有 `LOCAL_REQUEST → LOCAL_CLAIM → LOCAL_APPROVAL_REQUIRED → LOCAL_APPROVAL_DECISION → LOCAL_STARTED → LOCAL_RESULT` 及停止、恢复、迟到和拒绝路径。实现前须先独立复验直接宿主申请、批准前不启动、过时批准、权限与版本边界，再接入目录和模型请求。

目录观察版本与权限/执行契约版本分别表达元信息变化和实际执行规则。技能内容继续使用现有版本固定和受控加载机制；热刷新不改写已固定包，也不向最终检查增加新材料。

部署兼容边界：新启动协议的 `toolVersion` 只反映基础执行契约与正文校验器，CLI 观察目录独立版本化；在新协议内，热更新和随后重启都不因 CLI 元信息变化使任务失效。旧版本曾把整份 CLI 目录和正文校验器混合散列进 `toolVersion`，首次升级到本协议仍遵循既有配置不兼容恢复门，不静默重写旧契约、自动重放命令或宽泛接受旧批准。旧任务可按原门处理后停止或保留真实不完整结果，再新建任务。模型门槛包含既有 `configuration-recovery-model-fixture` 的复验；该一次性部署边界不应被描述成普通目录刷新造成的任务失效。

运行时完整快照由 `LocalRuntime.toolInventory()` 提供，包括 schema 与目录版本、观测时间、环境、完整 CLI 条目、完整技能元信息和刷新状态。运行器按已保存事实补充 CLI 身份、条目版本及沙盒/宿主各自的 readiness 来源与时间；模型适配器加入当前角色获准的内置接口，形成单一 `tool_inventory`。已有 `tool_guidance` 保留失败诊断。模型动作继续使用原有 `LocalAction`；单次决策所依据的条目快照由宿主保存并核对，不依赖模型自报版本来授予权限。

未登记命令仍可按既有显式 `runCli` 接口申请，并继续经过原权限、解析和授权守卫；目录缺失只表示未知，不宣称其已安装或把未知自动解释为不可执行。工具身份和选择期间条目变化核对针对本次快照中已登记的条目，无关目录变化不额外阻塞原来有效的动作。

来源刷新不能只以扫描函数返回为成功依据。技能根目录不可读取或已发布技能的必要元信息损坏，应使本次刷新失败，保留上一份有效 CLI 与技能的同一代快照，并公开失败来源；不能把剩余可读取条目拼成新的“完整”目录。正常移除技能属于有效目录变化，可以发布删除后的新观察版本。首次启动没有上一代快照、配置的技能源不存在，或扫描达到已声明数量与时间边界时，仍按 BT_Y129 保留来源诊断并如实报告不完整，不能扩大自动安装、执行或探测权限。来源完整性由同代注册表统一表达：`toolInventory().skills.complete`、`runtime.catalog().complete`、`registry.all().complete` 与 `discoverHost` 返回的 `skills.complete` 必须一致，不允许新目录报告不完整而兼容目录接口报告完整。
