# 正向推进的四项修正

需求来自对 PR #69 的四项流程复演。验收沿用真实任务状态机、持久领取和下游检查。

| 编号 | EARS 需求 | 契约 |
|---|---|---|
| FW-01 | 当分层摘要本轮所有分片结算后，系统应依据已保存的短产物和失败原因推进下一轮、交接顶层摘要或保存明确的停止原因。恢复旧的待结算快照时也应沿此路径推进。 | BT_Q55、BT_Q56 |
| FW-02 | 如果负责人的网页工具已用尽确定失败重选，且原窗口、预算和权限允许接续，系统应结算该负责人工作，把失败原因和已有材料交给协调员；如果普通额度已用尽，应保存带缺口的结果。 | BT_M66、BT_M67 |
| FW-03 | 当候选缺少必需的资源凭证且仍有检查额度时，系统应将候选与待补证资源交给当前下游检查。只有宿主核实真实凭证后才允许完整交付。仍缺凭证时应保存部分交付、下游已有修正和未核实原因。 | BT_E128、BT_E129 |
| FW-04 | 在负责人已有可领取、未到期的有效工作且没有重复失败证据时，如果进展期限到达，系统应保留原工作，不因定时检查重新派发。 | BT_O12 |

核查：分层轮次结算可以复用同一队列与持久产物，普通讨论仍按原契约作语义归并。网页失败次数、权限、物理效果核对和窗口期限仍由现有守卫约束。资源凭证的匹配、完整性与时效条件沿用当前宿主判据；有内容缺口也允许检查已交付的其他部分。进展期限可以继续识别已有重复失败记录，正常待领取工作与缺少有效路径可区分。

## 偏差与修正

| 编号 | 偏差类别与根因 | 实现和验证边界 |
|---|---|---|
| FW-01 | 状态模型把仅由已保存结果决定的分层结算交给模型回复。该回复丢失或无效会阻断下一层或负责人。 | 分层队列在最后一片结算后直接推进。恢复旧快照时沿同一路径结算。真实 XState 场景覆盖仅够一次分片和一次续办的额度、旧结算工作退休及幂等恢复。 |
| FW-02 | 已知网页失败用尽后，执行器丢失分类，普通失败转移进入没有待办的等待态。 | 执行器回传结构化失败。状态机保留原因和已有阶段产物，直接交给协调员或在额度用尽时保存部分交付。真实执行器场景核对第三次失败和协调意图。 |
| FW-03 | 提交候选时就检查必需获取凭证，导致下游无法尝试补证。 | 将已保存候选、待补证目标和既有材料交给一次下游检查。发布时按原宿主规则验证。真实 HTTP、SQLite 和执行器场景核对下游补证及引用。同一状态机在仍缺凭证时保留修正稿和未核实状态。 |
| FW-04 | 定时进展检查缺少监督已有的有效工作判断。 | 引擎和状态机共用守卫。验收场景在进展期限到达后通过引擎领取同一原工作。 |
