# Map 分片的排队与执行期限

原始要求来自调度架构审计后的分片期限调整。排队受任务总窗口和已存在的修复窗口约束，领取后才开始计算单次执行时间。保留到期拒绝、失败重试、迟到结果和旧快照规则。

| 编号 | 要求 | 验收 |
| --- | --- | --- |
| MAP-T01 | 当分片尚未领取且所属窗口有效时，系统应允许分片等待空位或等待领取。当该分片首次获准领取时，系统应从领取时间计算单次执行期限，并受分片原窗口及当前任务窗口约束。 | BT_Q32、BT_Q63 |
| MAP-T02 | 如果任务总窗口或适用的修复窗口到期，系统应拒绝尚未领取的分片并保留未完成记录。如果已领取的执行超过其期限，系统应拒绝迟到结果，且不得以这次超时增加自动重试。 | BT_Q32、BT_Q64 |
| MAP-T03 | 当系统恢复已保存的分片时，系统应保留旧快照已有的绝对期限和已领取尝试的执行期限。只有满足现有重试权限的独立新尝试才能获得自己的执行时间，且不得超出分片窗口。 | BT_Q28、BT_Q29、BT_Q33、BT_Q65 |

核查结果：三项均可通过队列状态、领取回执、工作期限、原始结果与尝试计数验证。继续使用任务状态机和原领取许可。变更适用于普通分片和复用同一队列的层次摘要、组内归并；原非分片工作时限无须调整。旧快照已保存的期限继续约束原工作，无需新的迁移版本或回填授权。

## 验证

- 真实 XState `verifyMapQueueModel` 重放了首批超时、分配后等待领取、总窗口和修复窗口到期、恢复后的旧期限、独立重试的领取和迟到结果。原模型在空位补派、延迟领取、修复窗口守卫和旧待办结算四处触发了反例。
- 直接执行 BT_Q32、BT_Q63–Q65 共五个实例，通过 416 步。分片调度、窗口、分层摘要和结果归并的关联场景共通过 52 个实例、4,334 步。业务时钟及提供方响应由夹具控制，执行接线使用实际状态机、TeamEngine、WorkRunner 和 SQLite。
