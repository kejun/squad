# 独立成员评审

用户要求让可独立开展的成员评审并行收集，同时保留存在前序依赖的评审顺序。现有全员评审每次只派发一项，下一位必须等上一位结算。已有普通求助、并行分片和宿主权限约束仍适用。

| 编号 | EARS 要求 |
| --- | --- |
| REVIEW-01 | 当用户直接要求多位成员独立评审，且评审范围、成员与额度可用时，系统应在同一材料和目标版本上并行派发这些成员，并在所派发成员结算后安排负责人汇总一次。 |
| REVIEW-02 | 当用户直接要求成员依次评审或基于前一位意见评审时，系统应按成员顺序派发，并向后续成员提供已结算的前序意见。 |
| REVIEW-03 | 如果成员失败、超时或额度不足，系统应如实保留缺口，在可用额度内结算其余已承诺工作，并为负责人保留汇总机会。 |
| REVIEW-04 | 当暂停、恢复、补充用户输入或目标版本变化发生时，系统应保留有效的已保存意见、隔离失效意见，并且只消费同轮同版本的每份结果一次。 |
| REVIEW-05 | 当用户明确跳过一位独立评审成员尚未启动的宿主操作时，系统应记录该成员的缺口，在原权限边界内继续其余评审。 |

REVIEW-01 与 REVIEW-02 对应 BT_G04 和 BT_G23。REVIEW-03 对应 BT_G24，REVIEW-04 对应 BT_G26。REVIEW-03 与 REVIEW-04 延续 BT_G09–G14、BT_J02、BT_J05。REVIEW-05 对应 BT_G25 和宿主权限契约 BT_Y104。用户直接请求仍是成员名单和前序依赖的依据。执行权限、成本预留、轮次隔离和普通求助的顺序语义沿用现有约束。五条要求覆盖派发、汇总、失败和恢复，并可用固定输入与受控结算顺序验证。
