# 输入意图与任务 OKR

原始要求为「用户发一条指令，意图识别后内部明确最终目标并生成 OKR+分工规划，不用体现在 UI 上」。沿用「OKR 由 LLM 生成，人来改」和「指导性机制，简单关联和状态标记」的要求。

| 编号 | EARS 需求 | 核查 |
| --- | --- | --- |
| IOKR-01 | 当用户提交普通新任务且已开启模型意图识别时，系统应在同一次意图请求中提炼最终目标、生成少量指导性关键结果，并根据已有分片能力决定由主笔直做或提出分工。 | 原目标字段作为 O，既有分片协议承载分工。短任务也适用，明确控制指令、点名快速路径、已提供结构化任务目标的 SDK 请求和仅够主笔执行的额度沿用当前入口。 |
| IOKR-02 | 当用户在当前任务的后续消息中明确修改关键结果或其状态时，系统应在当前目标版本记录修订，并将最新结果交给后续执行成员。 | 普通群聊消息是唯一入口。状态沿用任务意图快照。任务目标版本和宿主调度权限保持原语义。 |
| IOKR-03 | 如果模型省略关键结果或关键结果格式无效，系统应继续应用合法的目标和分工。如果用户未要求将某关键结果作为交付条件，系统应继续使用原有交付判据。 | 自动生成的关键结果可缺省。验收沿用直接用户要求，网页无需新增展示或控制。 |

验收为 BT_I25–BT_I29，状态见[输入意图解析](../state-diagrams.md#输入意图解析)。

## 验证记录

- 实现适配器前运行真实 XState 夹具 `node --import tsx tests/internal-okr-model-fixture.ts`，覆盖同次解析后的主笔和分片交接、当前任务修订、旧格式兼容和伪造引用拒绝。CI 单独重复运行该夹具。
- BT_I25–BT_I29 通过真实引擎、存储、执行器和模型适配器运行，替换供应商 HTTP。场景验证普通消息入口、SQLite 重开后修订、分片派发、交付判据以及非法结果处理。

## 已覆盖源码对应

产品提交 `fd687e5` 修改了六个已覆盖源码。九个入口的输入清单记录本次候选字节。

| 对应边界 | 核对结论 |
| --- | --- |
| 协调、协调扩展、交接、交接组合 | 普通新任务可以使用现有解释意图。仍经原事件、领取、额度和版本围栏；分片容量、执行队列与结果交接保持原路径。新增入口由真实状态机和 BDD 场景直接验证。 |
| 授权、授权组合 | 运行时仍校验用户动作和引用。关键结果为可选文字与状态，既有宿主继续决定成员、工具和外部权限。 |
| 交付 | 冻结候选、判据和发布继续沿用原路径。新增测试检查正常完成及关键结果与判据的隔离。 |
| 本地效果、宿主续办 | 工具协议、授权、执行、提交与恢复沿用原路径。意图解释不发起工具操作。 |
