# 处理窗口到期与明确续窗

原始要求：保留时间预算但延长为三小时；窗口到期应保存独立于网络 transient 的 `WINDOW_EXPIRED`，优先请求 `newWindow` 人类决定，不能静默 ended。

## EARS 与核查

| 编号 | 可观察要求 | 核查与验收 |
| --- | --- | --- |
| WIN-01 | 系统应为未显式配置时长的新任务建立三小时的固定自动处理窗口。 | 与原要求一致；保留显式配置、原快照截止时间及已用额度，不因恢复重新计时。BT_Y131、BT_Y01、BT_Y20。 |
| WIN-02 | 当尚未结束的任务达到原窗口硬期限时，系统应持久保存 `WINDOW_EXPIRED` 及原窗口身份，停止新业务派发，并打开提供 `newWindow`、明确结束和停止选项的人类门。 | 不将到期误作网络临时故障或自动结束；已存在的必需澄清或宿主批准不得被代答。BT_Y132。 |
| WIN-03 | 在窗口到期人类门打开时，如果用户没有明确授权新窗口，则系统应保持等待；当用户明确授权正时长新窗口时，系统应保存授权身份、更新截止时间并接续安全工作。 | 普通回复、重启和沉默不续期；历史计费、原成果、原回执和未知效果责任保留；续窗不批准宿主命令。活动任务从通用继续入口授权新窗时也应复用同一个门决定、保持原 epoch；该入口不能代答已有必需问题。已领取输入解析可通过新的安全意图继续；未完成协助退休且问题和已有答复历史保留，已保存结果仍走原 HELP_RESULT 唯一消费；所有活动阶段续窗后都应具有可交付并独立检查的路径。跳过旧命令或原问题只省略指定内容，仍请求续窗；仅到期窗口门的明确结束冻结全部任务。未开始与未完成的分片保存到期缺口，负责人在新窗通过新取得的完整可信来源逐片补齐并独立检查，不能重放旧物理操作。BT_Y133。 |
| WIN-04 | 如果失败的语义是窗口到期，则系统应使用 `WINDOW_EXPIRED` 且不得进行 transient 网络重试；当用户明确结束或停止时，系统应保留已有成果和缺口并形成明确逻辑结果。 | 处理窗口与较短的单次工作期限、修复期限分开；网络重试在原窗口内沿用原额度。BT_Y134。 |

核查结论：四条完整保留用户目标，触发与结果均可通过持久任务快照及网页观察；无关键未决产品问题。三小时是默认值变更，不改写已授权的持久窗口。有限修复耗尽、额度耗尽、用户停止仍保留原明确收敛语义。旧场景中的“窗口到期直接冻结”与本次要求冲突，按新要求改为先请求续窗；需要冻结的场景通过明确结束决定触发，而不移除部分成果、未知效果、迟到回执的保护。

## 数据与权限边界

处理窗口保存其失败 `{ code: WINDOW_EXPIRED, at }`；人类门保存原 `windowId`、`cause: windowExpired` 和相同显式 code。`WORK_FAILED` 可携带稳定 code；该 code 即使错误地附带 transient 也不能获得自动网络重试。新窗口由直接人类事件授权，不能由模型结果、工具正文或时间流逝创建。

任务真实 XState 沿用 `waitingHuman`，不另建 UI 状态。过期时保存取消意图并将物理未决移交独立清理；结果只结算原操作，不恢复过期工作。已有必需门的身份与待答语义优先保留，明确答复后再请求续窗，不能把回答原问题当成授权新窗口。单次宿主授权仍校验原命令、期限和批准身份。

## 已执行的门槛与接线

- 实现前先执行 `env -u MODEL_API_KEY node --import tsx tests/window-expiry-model-fixture.ts`，旧默认 `900000` 对三小时 `10800000` 断言真实失败；纯模型通过后才接 Runner、ModelAdapter 与网页。
- 续窗追加模型路径先检出两项实际缺陷：已领取输入解析没有新后继、未开始分片被取消后不能进入补齐协议。修正纯上下文后再次通过同一真实 XState 门槛；每个公开事件都 persist/restore。
- 模型覆盖六个活动阶段，保留旧必需批准、撤销到期 approveSession、明确新窗不恢复宿主批准，区分修复期限，接管物理未决，以及一成功加七缺口（含未开工）的原身份保留和负责人独立核验补齐。时间推进不重放原物理操作。
- `features/54_task_resilience.feature`、`features/61_host_approval_gate.feature` 与 `features/66_window_expiry.feature` 直接执行 130 场景、8543 步通过，Y134 同时经过实际 ModelAdapter → WorkRunner → 持久事件接线。完整集成、浏览器及负控证据由本轮验证记录承接；这些有界轨迹不声称证明所有模型或外部环境。

通用继续入口另有反例：旧 `CONTINUE(newWindowMs)` 把活动 map 的 epoch 从1变为2，导致原分片不再合法补齐。新增场景先复现该失败，再复用原人类门的 newWindow 决定；两种入口均保留原 epoch，并经完整来源与独立检查完成。原必需问题通过通用续窗入口被明确拒绝。

续窗交付轨迹又先检出旧协助 status=running 在其执行已结算后继续阻塞检查的缺陷。到期只取消当前尚未取得结果的协助等待，原问题与答复字段保留；已保存结果在新窗仍按原 HELP_RESULT 消费一次。六个活动阶段均完成续窗、负责人交付、独立检查和 complete，另验已保存答复的重复消费拒绝。旧宿主命令门 skip 先记录指定缺失，再请求新窗；仅窗口门的明确结束冻结整个任务。
