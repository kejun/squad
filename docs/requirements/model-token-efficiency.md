# 模型请求的 token 效率

| 编号 | EARS 需求 | 核查与验收 |
| --- | --- | --- |
| TOK-01 | 当模型收到 `discoverHost` 的技能候选时，系统应仅为每条候选提供 `skillId`、名称和用途。当 `loadSkill` 成功时，系统应以宿主凭证固定实际版本。 | 沿用候选集合、CLI 召回及版本绑定。覆盖旧回执、目录变更及激活后的读取。 |
| TOK-02 | 在已配置模型支持前缀缓存时，系统应提供稳定的指令前缀，并在供应商报告用量时记录其缓存读写。 | 不依赖兼容端点支持额外请求参数。通过相同工作连续请求的序列化结果和供应商用量样本验收。 |
| TOK-03 | 当模型返回已知工具的畸形参数时，系统应先本地校验。能安全等价修正时应直接复验，否则在现有额度内最多发送一次只针对该动作的修正请求，并在执行前复验。 | 保留工具权限和状态守卫。未知输出仍走既有协议；停机、额度耗尽或修正仍不合规时拒绝执行。覆盖同一次工作内的检查动作和已完成操作不重放。 |
| TOK-04 | 当独立检查开始时，系统应发送当前交付全文、全部判据及其用户原始约束。当判据需要来源时，系统应允许检查员在现有额度内按固定引用查读保存证据。如果来源不可核实，则检查员应标记对应判据无法核实。 | 冻结材料保留在宿主，首轮只提供查读所需的来源索引。保持候选版本、取证权限、补试与发布守卫。容量不足时仍应明确结束。 |

核查结论：四项分别对应用户确认的发现、缓存、协议修正和检查输入。裁剪只影响发送给模型的材料；验收检查以当前候选和原始用户要求为准。缓存用量和实际发送量分别观测。实测应比较整次 check 的输入、往返和判据结果。

状态对应关系：`REGENERATE_MODEL_OUTPUT` 只在已有模型请求、当前工作有效且两种额度充足时授予一次单动作修正。状态机仍分开记录模型请求与工具执行，最终检查 JSON 仍走原技术补试。`LOCAL_REQUEST` 的动作、权限、持久化和执行守卫保持原语义。证据分页只读已绑定的 `CheckMaterials`，使用 `CONSUME` 授权下一次模型请求。缓存和发现投影均在模型传输边界，无任务状态转移。
